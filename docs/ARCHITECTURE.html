aops v2 설계안 · 아키텍처

에이전트의 전 라이프사이클을 관리하는 래퍼. 실행 엔진은 만들지 않고, Claude Code·Codex 같은 하네스와 Databricks·Omnigent를 감싼다. 하네스를 바꿔도 세션과 메모리가 이어진다.

대상은 개발자(원해서 기록·평가)와 관리자(등록·배포 형식 관리). 원칙은 개발은 자유, 등록부터 강제.

결정 사항

개발은 자유, 등록부터 강제
· 개발자는 원해서 기록하고 평가한다. hook·기록·가드레일은 언제든 끌 수 있고, 끄면 기록이 남지 않을 뿐이다. aops는 끈 것을 되살리거나 뒤에서 채우지 않는다. aops로 실행하면 기록된다.
· 개발 중 가드레일은 시험 도구다. 개발자를 막는 장치가 아니다.
· 강제는 dbx·omni의 validate → register → deploy(→ approve·promote)에서 관리자 정책을 코드로 검사할 때만. local에는 강제가 없다.
· 강제 검사는 개발 중 기록에 기대지 않는다. 증거는 validate Job이 등록할 소스로 직접 만든다.
개발 기록 위치aops로 실행하면 기록된다. 위치는 사용자가 정한다. local은 프로젝트 폴더, dbx 기본은 본인 Experiment(/Users/<me>/aops/…). 공유 위치는 사용자가 고를 때만
하네스 전환 시점사용자가 정한다. aops는 자동 전환·사용량 한도 감지를 하지 않고, 전환되면 맥락만 이어 붙인다
로그인aops는 제공·제한하지 않는다. 사용자가 하네스에 설정한 로그인을 그대로 쓴다. 구독 로그인은 사용자가 설치한 하네스를 구동하고 자격 증명을 다루지 않는다
dbx 모델 호출Unity AI Gateway 경유를 권장(강제 아님). 사용량·예산·기록이 자연스럽게 남는다
평가 기록aops evaluate는 MLflow에 기록. local은 프로젝트 MLflow, dbx는 Databricks Experiment
세션 정본local·dbx는 aops. omni는 Omnigent가 세션을 갖고 aops는 인계·비교·평가를 맡는다
1차 지원 하네스Codex, Claude Code. 나머지는 어댑터 인터페이스만 두고 뒤로
에이전트 서버 (dbx)Agent Bricks DurableAgentServer(server = "agentbricks")만. legacy Responses 서버(MLflow AgentServer·LongRunningAgentServer)는 쓰지 않음. 로컬 채팅은 agentbricks dev
검증 실행 (dbx)aops validate = Lakeflow Job(서버리스). 이 Job 결과만 배포 승인 근거
레지스트리·승인 (dbx)레지스트리, 배포 요청, 승인·반려, 배포·운영 지정 이력은 UC Delta 테이블이 정본
운영 화면 (dbx)모니터링·레지스트리·승인은 Databricks App(console App). 배포 승인은 이 화면에서만. CLI aops monitor는 보조
실현 가능성 요약 (하네스 소스·패키지·공식 문서·워크스페이스 조회로 확인, 상세는 14장)
  • 핵심 기능(하네스 간 이어가기)은 만들 수 있다. 다만 하네스 내부 상태를 그대로 옮기는 것이 아니라 요약·인계 파일·기록 조회 도구로 이어가는 방식이다.
  • 터미널 직접 실행 기록과 hook 가드레일은 막힐 수 있다. Codex는 hook마다 사용자 승인이 필요하고, 회사 관리 설정이 프로젝트 hook을 끌 수 있다.
  • dbx 기능 다수가 Beta이고 서비스 정책 부착은 UI 전용이다. Codex·Claude 기반 에이전트의 Apps 배포는 실제 배포로 확인해야 한다.
  • aops monitor의 "실시간"은 Databricks가 앱 실행 상태까지만 준다. 진행 중인 세션·방금 쓴 MCP는 aops가 배포 에이전트에 상태 경로(/aops/status)를 넣고 Apps telemetry를 켜서 만든다. 사용량은 1시간, 비용은 최대 12시간 늦다.
  • 구독 로그인: 제3자가 사용자 대신 구독 자격으로 요청을 보내는 것을 Anthropic이 허용하지 않는다. aops는 자격 증명을 다루지 않고 사용자 설치본을 구동하며, 공개 배포 전에 확인한다.
  • dbx는 Databricks 기능 위에서 돈다: Durable 서버, agentbricks dev, Lakeflow Job 검증, Delta 레지스트리·승인, Databricks App 운영 화면 (3장 기능 표).

1핵심 기능: 하네스를 바꿔도 이어지는 세션과 메모리

Claude Code를 쓰다 사용량이 떨어지면 Codex로 옮기는 경우가 많다. 하네스마다 세션·메모리를 따로 저장해서 맥락이 끊긴다. aops가 세션의 정본을 갖고, 전환할 때 맥락을 이어 붙인다.

이어 붙이는 4가지

대상전환할 때
대화 기록요약 + 최근 턴을 넘기고, 나머지는 필요할 때 조회
작업 상태프로젝트 폴더는 그대로, 변경 요약(git diff·계획)만 넘김
요약전환할 때마다 원본 기록에서 새로 생성 (기본: 모델 없이 규칙 기반)
장기 메모리현재 일과 관련된 항목만. 변경은 제안 → 사용자 승인

기록 범위

  • aops로 실행 (aops run, 개발 화면): 어댑터가 기록
  • 프로젝트 폴더에서 claude·codex 직접 실행: aops가 넣은 프로젝트 hook이 턴마다 기록
  • 이미 끝난 세션: aops session import
터미널 기록이 동작하는 조건
Codex: 프로젝트를 신뢰로 승인하고, hook마다 /hooks에서 승인해야 한다(내용 해시 기준, 바뀌면 재승인). aops가 대신 승인할 수 없어 hook은 내용이 바뀌지 않는 한 줄(aops hook <이벤트>)로 둔다.
Claude: 대화형은 처음에 신뢰 확인. -p·SDK는 확인 없이 프로젝트 hook을 실행한다.
공통: 회사 관리 설정(Codex features.hooks, Claude allowManagedHooksOnly)이 막을 수 있다.
사용자가 끈 기록은 되살리지 않는다. hook을 지우거나 끄면 그 구간은 기록되지 않는다(의도한 동작). aops는 설정을 다시 만들 때 지운 hook을 넣지 않고, 하네스 기록은 사용자가 직접 session import할 때만 가져온다. aops doctor는 "기록 꺼짐"을 알리기만 한다.

인계 방법: 한꺼번에 넣지 않는다

hook이 넘기는 문맥에는 크기 기준이 있다(Codex 약 2,500 토큰, Claude 10,000자). 넘으면 파일로 빠지고 미리보기만 넘어가므로 나눠서 넣는다.

구성내용
인계 파일.aops/handoff/<session>.md: 요약·최근 턴·작업 상태·메모리. 하네스별 토큰 예산에 맞춤
짧은 안내SessionStart hook으로 "이어받은 세션, 인계 파일과 조회 도구를 먼저 확인"
조회 도구aops-recall MCP: 이전 턴 원문·도구 결과·변경 내역을 새 하네스가 필요할 때 꺼냄
Codex 기록 주입aops가 Codex를 구동할 때 thread/inject_items(안정 API)로 이전 대화를 Codex 기록에 직접 넣음. Claude에는 이런 방법이 없다

한계: 도구 실행 원본·추론·프롬프트 캐시 같은 하네스 내부 상태는 옮길 수 없다. 새 하네스는 요약과 조회 도구로 맥락을 다시 잡는다.

함께 처리하는 것

  • 하네스 고유 재개: 하네스 상태를 구간마다 보존. 같은 실행 파일·같은 버전일 때만 --resume·thread resume (버전 간 재개 보장 없음. Claude 세션은 30일 뒤 삭제되므로 원본은 aops가 보관)
  • 끝나지 않은 턴: 턴마다 git 상태·도구 실행 기록으로 체크포인트. 이미 바뀐 것을 보여주고 사용자가 "이어서 / 다시" 선택
  • 개인정보: 저장 전 2층 규칙으로 가림, 원문 저장 끄기 가능 (dbx 기본 끔)
  • 품질 시험: aops evaluate --suite handoff → MLflow

시험

비교

배포

aops deploy가 [release.guardrails]를 함께 배포한다(개발 중 스위치가 꺼져 있어도 무관). Gateway 정책은 공개 API로 붙이거나 조회할 수 없어(UI 전용) 점검표 + 시험 질문으로 실제 차단을 확인. omni는 CEL 정책으로.

제한 · hook 가드레일은 완전한 차단 경계가 아니다(Codex 웹 검색 미적용). 개발 중에는 시험 도구라 이것으로 충분하고, 사용자가 끄는 것도 허용한다. 운영에서 반드시 막을 규칙은 배포 에이전트 쪽(배포 패키지 규칙, Gateway 정책)에 두고 validate가 검사한다. 개발 PC 통제는 aops 범위 밖이다. · Gateway 서비스 정책은 Beta이고, 차단돼도 HTTP 200에 안내 문장이 온다. · 관리형 Omnigent 정책은 CEL만 된다.

6하네스 어댑터

어댑터가 하는 일

  1. aops.toml → 하네스 프로젝트 설정 생성 (지시, 스킬, 도구, 가드레일 hook, 세션 기록 hook)
  2. 하네스 구동, 출력 원본을 runs/events/에 저장
  3. 원본 → aops 이벤트 (버전 있는 변환기)
  4. 세션 구간 기록, 하네스 고유 상태 보존
  5. 인계 내용을 하네스 방식으로 주입
  6. 시작 시 지원 기능 확인, 없는 기능은 화면에서 끔
  7. 로그인은 건드리지 않음: 사용자 설정·API 키·Gateway 토큰 그대로

  • compat.toml은 CI가 uv.lock에서 생성
  • aops 버전 = 검증된 상위 버전 묶음 (상위 변경 minor, 비호환 major)

  • agentbricks dev: 배포와 같은 명령·환경으로 포트 8000, LangGraph 템플릿은 채팅 화면 기본 포함, 로컬은 세션·메모리 미연결. agentbricks tools add sandbox가 system.ai.sandbox MCP를 권한 축소와 함께 붙임
  • MLflow deployment jobs: UC 모델 버전 → 평가·승인·배포 Job. 승인은 UC 태그 Approved, 승인자는 APPLY TAG·CAN MANAGE RUN 필요, governed tag로 자기 승인 차단. Public Preview
  • multi-statement transaction: BEGIN ATOMIC … END, 최대 100개 테이블, catalog commits UC managed만(delta.feature.catalogManaged = 'supported', 기본값 아님), DDL 불가. 시험 워크스페이스에서 두 테이블 동시 커밋과 쓰기 뒤 실패 시 롤백 확인
  • Apps telemetry: otel_metrics·otel_spans·otel_logs, FastAPI 자동 계측, 지원 지역 14곳(ap-northeast-2 포함)
  • 사용량 테이블 컬럼(조회): requester, requester_type, service_type(MODEL·MCP), mcp_metadata.tool_name, session_metadata.coding_agent, request_tags, service_policies. 최근 30일 /ai-gateway/codex·/ai-gateway/anthropic 두 경로의 호출 기록 확인
Omnigent 세부 근거 (0.20.0 OSS)
  • 공식 문서 "Omnigent is in Beta", README "Status: alpha", Apache-2.0. Python 3.12+, Node.js 22+, tmux 필요. 패키지 미러에 따라 빈 예약 패키지가 받아질 수 있음
