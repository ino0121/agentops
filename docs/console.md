# console 화면

aops 서버 주소를 브라우저로 열면 나오는 화면입니다. dbx 에디션의 등록·배포 명령을 모두 화면에서 합니다. 화면은 CLI와 같은 `/api/v1`을 부르므로, 어디서 하든 같은 레지스트리에 같은 기록이 남고 같은 규칙(평가 Gate, 승인, 본인 승인 금지)이 적용됩니다.

## 화면과 명령

왼쪽 메뉴는 네 묶음입니다: **작업**(에이전트·배포 요청함), **도구**(폴더·zip 등록·Genie 점검), **관리**(정책·평가 프롬프트), **도움말**(CLI·Genie Code). 맨 위 [+ 새 에이전트]가 만들기입니다. 화면마다 제목 옆에 같은 일을 하는 CLI 명령이 붙어 있습니다.

동작 이름과 표시는 어디서나 같습니다: ✎ 개발 · ✓ 셀프 체크 · ↑ 등록 · ◆ 평가 · ▶ 배포 요청 · ✔ 승인 · ⚑ 권한 · ↓ 가져오기. 종류는 네모 칩(스킬 보라·코드 파랑·노코드 청록), 상태는 둥근 배지(초록 통과·주황 주의·빨강 실패)로 구분합니다.

| 화면 | 하는 일 | CLI |
| --- | --- | --- |
| 에이전트 | 맨 위 **할 일**: 승인할 요청·진행 중인 내 요청·고칠 에이전트(평가 실패·부적합)·운영 중. 아래 목록은 이름·종류·운영·최신 버전·마지막 평가(한 단어)·진행 중 요청·담당. 찾기, 종류·상태(고칠 것 포함) 거르기 | `aops list` |
| 에이전트 상세 | 위에 **수명 주기 막대**: 개발 → 셀프 체크 → 등록 → 평가 → 승인 → 운영. 단계마다 지금 상태와 그 단계의 동작 하나(고칠 곳 열기, 셀프 체크, 등록, 평가, 리포트·승인, 운영 대상 열기). 오른쪽 위는 가져오기·권한·배포 요청. 아래 정보(담당·지정 승인자·중요도·민감도·보안 등급·작업 폴더 또는 에이전트 폴더·공개 그룹)와 탭(버전·평가·배포 요청·배포·이력) | `aops list`, `aops gates` |
| 셀프 체크 | 템플릿 구성 체크리스트([규칙](validate.md): 규칙마다 ERROR·WARN과 고치는 곳). 워크스페이스 폴더·등록 버전·올린 폴더, 노코드는 지금 개발용 Genie. 기록하지 않음 | `aops validate` |
| 평가 | evaluate Job(Gate): 형식 검사 → 내용 검토(모델이 모든 파일을 읽고 체크리스트 리포트) → 품질 평가. 끝나면 리포트가 같은 창에 나옴. 평가 탭의 [리포트] | `aops evaluate` |
| 배포 요청 | 버전을 골라 요청 → 평가 → 승인 → 운영 반영 진행을 실시간으로. 운영보다 낮은 버전은 ↺ 되돌리기. 노코드는 버전 없이 요청(스냅샷), 배포가 성공할 때 버전을 매김 | `aops deploy`, `aops deploy --version` |
| 권한·가져오기 | 권한: 스킬 UC Skill 읽기, 코드 앱 `CAN_USE`, 노코드 운영용 Genie `CAN RUN`. 가져오기: 스킬 운영 버전 zip, 코드 운영 앱, 노코드 운영용 Genie | `aops promote`, `aops load` |
| 배포 요청함 | 승인할 요청(내가 지정 승인자인 것)·내 요청·전체. 줄마다 상태·내용 검토 판정·승인자·요청자. 줄을 누르면 **배포 요청 화면**: 평가 → 승인 → 운영 반영 진행, 요청 정보, 승인자 결정(리포트 확인 체크·의견·승인·반려), 평가 리포트 | `aops gates [<gate>]`·`approve`·`reject`·`deploy --cancel` |
| + 새 에이전트 | 번호 붙은 다섯 구역: ① 종류 ② 기본 정보(이름·표시 이름·설명) ③ 분류(중요도·민감도·보안 등급·담당 팀) ④ 승인자(워크스페이스 사용자·그룹 찾기) ⑤ 만들 곳(스킬: 기본 하네스·내 워크스페이스 위치, 코드: 프레임워크 LangGraph·OpenAI Agents SDK·내 워크스페이스 위치, 노코드: 개발용 Genie·내가 SELECT할 수 있는 테이블·warehouse·공개 그룹). 오른쪽은 종류별 "만든 뒤 흐름"(같은 6단계) | `aops init`, `aops init --type code --framework langgraph` |
| 폴더·zip 등록 | 에이전트 폴더(또는 버전 zip)를 올리거나 워크스페이스 폴더 경로를 적어 새 버전 저장. 폴더는 서버가 CLI와 같은 규칙으로 묶어 해시까지 같음 | `aops register` |
| Genie 점검 | 아무 Genie 스페이스 정의를 노코드 정의 규칙(15개)으로 바로 점검하고 고치는 곳을 보여 줌. 기록하지 않음 | `aops validate --agent` (노코드) |
| 정책·평가 프롬프트 | 지금 정책과 이력. 관리자는 평가·승인 방식, 승인 그룹, 지정 승인자 필수 여부를 바꿈(새 정책 버전). 평가 프롬프트 4개를 버전으로 고침 | `aops admin setup --only policy` |
| CLI·Genie Code | 명령 ↔ 화면 ↔ API 대응표 | `GET /api/v1/meta/commands` |

## 스킬·코드 기반을 워크스페이스에서

1. **새 에이전트 → 스킬 기반·코드 기반 → [내 워크스페이스에 만들기]:** `aops init`과 같은 템플릿(SPEC 항목이 든 `SPEC.md`, 이 서버 주소가 든 `aops.toml`)이 내 토큰으로 `/Workspace/Users/<나>/aops/<이름>`(또는 적은 위치)에 올라갑니다. 이미 있는 폴더에는 쓰지 않습니다. 하네스 설정(`.claude`·`.agents`·`CLAUDE.md`·`AGENTS.md`)은 올리지 않습니다. 에이전트가 레지스트리에 바로 잡힙니다(버전은 등록 때).
2. **[폴더 열기] · [편집기에서 열기 (Genie Code)]:** 폴더 열기는 워크스페이스 화면에서 그 폴더를 엽니다(파일을 더하거나 지울 때). 편집기 링크는 파일만 열고 왼쪽 파일 트리는 폴더를 따라가지 않으니, 파일을 새로 만들 때는 폴더 열기로 갑니다. 코드 기반은 `agent/agent.py`, 스킬 기반은 `agent/skills/my-skill/SKILL.md`가 편집기에서 열리고 오른쪽에 Genie Code가 있습니다. 고칠 내용을 말하고, 다 되면 "이 폴더를 aops에 등록해줘"라고 하거나
3. **[이 폴더에서 등록]:** 서버가 내 토큰으로 그 폴더를 읽어 `aops register`와 같은 규칙으로 묶습니다(해시도 같음). 에이전트 화면의 수명 주기 막대 "개발" 단계에도 [폴더]·[편집기] 링크가 있습니다. 노트북은 묶지 않으니 코드는 파일(Create → File)로 만듭니다.

PC에서 고치려면 [폴더 받기 (zip)]로 같은 템플릿을 받습니다.

## 노코드 (Genie Agent)

1. **새 에이전트 → 노코드:** SPEC 항목과 개발용 Genie를 정합니다. 테이블로 새로 만들기(표준 지침 PURPOSE·CONSTRAINTS·요약 지침이 들어감), 기존 스페이스 복사(원본 그대로), 기존 스페이스 옮기기(ID·대화 이력 유지). 공개 그룹(`consumer_group`)은 배포 때 운영용 Genie에 `CAN RUN`을 받습니다.
   - **데이터 고르기:** 카탈로그 → 스키마를 고르면 **내가 `SELECT`할 수 있는 테이블**만 나옵니다(Unity Catalog가 내 토큰으로 거른 목록, `BROWSE`만 있는 것은 빠짐). 이름·설명으로 찾고, [컬럼]으로 컬럼을 보고, 여러 스키마에서 30개까지 고릅니다(메트릭 뷰는 정의의 `metric_views`로). 고른 테이블마다 **aops 서비스 주체가 읽을 수 있는지** 표시합니다: 운영용 Genie는 서비스 주체 권한으로 돌기 때문에 `SELECT 없음`이면 첫 배포 전에 데이터 주인이 권한을 주어야 합니다. 목록을 못 쓰면 [직접 입력]으로 이름을 적습니다.
   - **warehouse:** 내가 볼 수 있는 SQL warehouse 목록에서 고릅니다(aops 기본이 먼저). **복사·옮기기:** 내가 열 수 있는 Genie 스페이스를 제목·설명으로 찾아 고르거나 주소·ID를 붙여 넣습니다.
   - aops 서비스 주체가 에이전트 폴더 `/Workspace/aops/no-code/<이름>`을 만들고 나와 담당 팀에 `CAN MANAGE`를 줍니다. `SPEC.md`가 그 폴더에 생기고, 여기서 고치면 다음 배포 요청에 들어갑니다.
   - 개발용 Genie는 **내 토큰**으로 그 폴더에 만듭니다(앱의 `genie` 사용자 권한 범위). 내 테이블·warehouse 권한이 그대로 적용되고, 서비스 주체는 폴더에서 권한을 받아 정의를 읽습니다.
2. **[Genie에서 열기]:** 개발용 Genie에서 예제 SQL·벤치마크·지침·컬럼 설정을 채웁니다.
3. **[셀프 체크]:** Gate와 같은 정의 규칙(15개)의 준수율과 고치는 곳. 기록하지 않습니다. **[평가]**는 배포 요청 없이 Gate만 돌립니다(아래 4의 평가).
4. **[배포 요청]:** 개발용 정의와 `SPEC.md`를 스냅샷으로 떠서 평가(`format`·`definition`·`secrets`, Genie 벤치마크 `evaluate`: 정확도·운영 버전 대비 회귀, `integrity`, `record`) → 정책대로 승인 → 배포 Job이 운영용 Genie(서비스 주체 소유, `/Workspace/aops/no-code/_production/<이름>`)를 만들거나 고침 → 이때 버전 등록(처음 1.0.0, 데이터 소스가 바뀌면 major, 그 밖 minor). 검사가 끝날 때까지 개발용을 고치면 `stale`로 반려됩니다.
5. **[권한]·[가져오기]:** 운영용 Genie `CAN RUN` 부여·회수, 운영용 Genie 열기. 받은 사람도 테이블 `SELECT`와 warehouse 사용 권한이 있어야 답을 받습니다.

운영용 Genie는 서비스 주체가 만들고 벤치마크도 서비스 주체로 돌므로, 쓰는 테이블에 서비스 주체의 `SELECT`가 필요합니다.

화면에 없는 것: 하네스 실행(`aops run`, `aops session`)은 PC나 Genie Code에서 합니다. 레지스트리·서버·Job·권한 설치(`aops admin setup`의 정책 외 단계)는 관리자 CLI입니다.

## 평가 리포트와 승인

배포를 요청하면 평가(Gate)가 **승인자용 리포트**를 씁니다. 배포 요청함 → [리포트 보고 결정](또는 배포 진행 창의 [리포트 보기])이 그 화면입니다.

- **종합:** 내용 검토 판정(적합·주의·부적합), 검토 모델의 권고(승인해도 됨·고친 뒤 다시 요청·내보내지 말 것), 요약, 의견
- **체크리스트:** 항목마다 판정, 사유, 근거(파일:줄과 발췌). 부적합·주의가 위에 옵니다. 검토 범위(읽은 파일·줄), 쓴 프롬프트 버전, 모델
- **품질 평가:** 정확도와 문항별 판정·정답·답 (스킬 평가셋, 노코드 벤치마크)
- **형식 검사:** 셀프 체크 규칙의 결과 (펼쳐 봄)
- **승인자 결정:** 지정 승인자(없으면 승인 그룹)에게만 보입니다. "리포트를 확인했습니다"를 체크해야 [승인]이 됩니다. 반려는 사유가 필요합니다. 본인 요청은 승인할 수 없습니다. 단, 정책의 **개발용 예외 승인자**는 혼자 시험할 수 있게 본인 요청도 결정할 수 있고, 화면에 "개발용 예외로 결정합니다"가 뜨며 감사 이력에 예외로 남습니다.

리포트의 부적합, 검토 모델의 "고친 뒤 다시"·"내보내지 말 것" 권고, 품질 기준 미달은 요청을 반려하지 않습니다. 승인자가 판단하고, 그 요청은 자동 승인되지 않습니다. 검토 모델을 부르지 못해 내용 검토를 못 했을 때도 반려하지 않고 승인자에게 그렇게 알립니다.

**정책 → 평가 프롬프트:** 내용 검토의 프롬프트 4개(공통·스킬·코드·노코드)를 관리자가 고칩니다. `## 체크리스트` 아래 `- <id>: <통과 조건>` 줄이 리포트 항목이 되고(미리 보기), 저장하면 그 종류의 새 버전이 됩니다. 버전 이력이 아래에 남고, 평가 기록에는 쓴 버전이 남습니다.

**승인자 고르기:** [새 에이전트]의 승인자 칸에서 이름·이메일로 워크스페이스 사용자·그룹을 찾아 고르거나 이메일·`group:<그룹>`을 적습니다. SPEC.md `approvers`가 되고, 배포 요청은 그 승인자만 승인합니다. 정책 화면의 "에이전트마다 지정 승인자 필수"를 켜면 이 화면은 승인자 없이 만들지 않고, 승인자가 없는 에이전트는 셀프 체크·평가에서 ERROR입니다(CLI·API로 만든 에이전트도 평가에서 막힘).

## 쓰는 법

- **Databricks App(aops 서버):** `aops admin setup`이 배포한 앱 주소를 엽니다. Databricks 로그인을 그대로 쓰고, 앱의 `CAN USE` 권한이 있으면 됩니다. 앱의 기본 사용자 권한 범위(`iam.current-user:read`·`iam.access-control:read`, 모든 앱에 늘 들어 있음)로 내 그룹을 읽어 담당 팀·승인 그룹·관리자를 판정합니다. `aops admin setup`이 더하는 범위: `files`(스킬 가져오기), `genie`(노코드 개발용 Genie를 내 권한으로, 스페이스 목록), `workspace.workspace`(내 폴더에 템플릿), `catalog.catalogs:read`·`catalog.schemas:read`·`catalog.tables:read`(노코드 만들기의 내 테이블 목록, 읽기만), `sql:read`(내 warehouse 목록, 읽기만). 범위가 바뀐 뒤에는 새로 로그인할 때 동의 화면이 나옵니다. 바뀌기 전에 연 화면(앱 세션)은 예전 범위의 토큰을 계속 쓰므로, 시크릿 창으로 열거나 앱 주소의 쿠키를 지운 뒤 다시 엽니다.
- **내 PC에서 시험:** 레지스트리에 연결한 `aops serve`를 띄우고 `http://127.0.0.1:8000`을 엽니다. 이때 화면의 사용자는 그 PC의 Databricks CLI 프로필 사용자입니다.

  ```bash
  AOPS_PROFILE=<프로필> AOPS_REGISTRY=<catalog>.<schema> AOPS_WAREHOUSE_ID=<warehouse> \
  AOPS_DIST_WHEEL=/Volumes/<catalog>/<schema>/aops_dist/aops_cli-<버전>-py3-none-any.whl aops serve
  ```

  `AOPS_DIST_WHEEL`은 운영 서버와 같은 경로로 둡니다(다르면 서버가 Job 설정을 그 패키지로 바꿈). PC에서 띄운 서버로 처음 등록하면 볼륨 주인이 그 사람이 되어 서비스 주체의 평가 Job이 읽지 못하므로, 시험용 등록은 운영 서버로 합니다.
- 화면은 빌드 없이 서버가 바로 내주는 파일 세 개(`src/aops/server/web/`)입니다. 외부 글꼴·라이브러리를 쓰지 않아 닫힌 망에서도 됩니다.
